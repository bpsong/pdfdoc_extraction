# PDF processing application audit

**18 November 2026 · Revision `ff60b7dab968ecd90101a9ab3b4a9611ee876fea` · Windows AMD64, Python 3.13.3, SQLite 3.49.1**

History cleanup can lead to deletion of a web-uploaded original on the next web startup. A long job can outlive its claim, and repeated worker crashes can take it beyond its configured attempt limit. Completing an ordinary review can also make other users wait while the web process executes the rest of the workflow. These are the highest-priority findings. The retention and retry findings were confirmed with temporary files and databases. The review finding follows the production call path.

The Windows supervisor, version pinning, review validation and admin checks all have direct verification. A temporary production-mode deployment reached readiness. The actual local signing key failed the production gate. No production endpoint, cloud account or backup was used. The active database was opened read-only for configuration counts. Findings below omit record identities, customer content and credential values.

**Verdicts.** *Proved* means a source path or isolated observation establishes the finding. *No issue* applies to the named control and scope. *Weak* means a limitation is visible but its operational impact is unmeasured. *N/A* means the mechanism does not apply to this implementation. *Blocked* identifies missing evidence. Severity describes impact in this application. Blocked items have unassessed severity.

## High severity

1. **Business logic — Proved. Cleanup breaks the file-retention promise.** Web uploads are finalized as `web-upload-{id}.pdf` under the processing directory. Cleanup removes eligible document and artifact rows, and reports zero files deleted. At web startup, reconciliation uses those two tables to decide which files to keep and unlinks unreferenced files matching that name. In a synthetic completed batch, reconciliation removed **0** files before cleanup. Cleanup reported **0** and the PDF still existed. The next reconciliation removed **1** and the PDF was gone. This affects originals still at that location when their last reference is purged. An independent archive copy, if present, is outside this deletion. The existing retention test uses a different filename and ends before reconciliation. [Retention contract](../../docs/admin/archiving-and-retention.md#what-cleanup-removes-and-retains) · [Upload filename](../../modules/api_router.py#L990) · [History deletion](../../modules/services/pipeline_cleanup_service.py#L171) · [Reconciliation](../../modules/services/upload_receiver.py#L409) · [Startup call](../../web/server.py#L145) · [Existing test](../../test/services/test_pipeline_cleanup_service.py#L35)

2. **Jobs — Proved. Lease recovery exceeds the retry limit and can overlap a live job.** The worker claims once before synchronous execution. Health heartbeats update component status independently of job ownership. The expired-lease update has no attempt ceiling, and the claim query increments the attempt count without checking the maximum. A temporary job configured for three attempts was claimed on attempts **1, 2, 3 and 4** after successive expirations. The ordinary exception-retry path does check the maximum. The local lease is **3,600 seconds**. An enabled locally published Split step permits **7,200 seconds**, leaving a **3,600-second** interval in which another polling worker could reclaim a still-running job. The standard supervisor starts one worker. Overlap requires another worker to poll. Duplicate provider calls or outputs were not observed. [Worker](../../modules/services/processing_worker.py#L40) · [Claim and expiry](../../modules/db/repositories.py#L533) · [Ordinary retry ceiling](../../modules/db/repositories.py#L614) · [Split timeout](../../standard_step/split/llamacloud_split.py#L58)

3. **Architecture and availability — Proved. Ordinary review completion runs downstream work on the web event loop.** The async HTTP handler calls the synchronous completion service directly. After committing corrections the service calls the resume manager, which invokes the synchronous flow inline. The serving process owns an exclusive lock for its processing directory. A slow downstream task can delay unrelated requests and HTTP readiness responses for the duration of its work. The incident duration under real workloads is unknown. Manual-split completion has a separate dispatch path. [HTTP handler](../../modules/api_router.py#L2704) · [Post-commit dispatch](../../modules/services/review_service.py#L466) · [Flow invocation](../../modules/resume_manager.py#L94) · [Web ownership](../../modules/services/upload_storage_lock.py#L46)

## External limits and local calculations

| Boundary | Verdict and severity | Calculation and source |
|---|---|---|
| Web upload versus cloud file limits | No issue · none for file size at current web settings | Local admission allows 50 MiB/file, 20 files/request, 200 MiB/request and 2 concurrent admissions. **50 × 1,048,576 = 52,428,800 bytes**. LlamaIndex publishes **100 MB** for Extract and **512 MB** for Split. A single maximum-size web upload fits either file cap. Four full-size files consume exactly 200 MiB before multipart framing, so at most **three full-size files** fit one request. Two admitted requests allow **400 MiB of request bodies** in total. That figure is neither resident memory nor total spool space. [Upload limits](../../modules/services/upload_receiver.py#L180) · [Byte counter](../../modules/services/upload_receiver.py#L213) · [Provider file limits](https://developers.llamaindex.ai/llamaparse/general/limitations/) |
| Cloud page limit | Weak · medium | Extract publishes a **500-page/job** cap. The standard web receiver checks suffix and PDF signature. The inline Extract path submits the file without a page-selection field. A small **501-page** PDF can pass these web checks while exceeding the published Extract limit by one page if all pages are selected. Split has no published page-count ceiling. Saved remote configurations may change page selection. [Web checks](../../modules/api_router.py#L974) · [Extraction request](../../standard_step/extraction/llama_cloud_v2.py#L145) · [Provider page limits](https://developers.llamaindex.ai/llamaparse/general/limitations/) |
| Cloud polling and retry budget | No issue · none for one default Split poller against the public rate | The locally enabled Split step sleeps one second between reads. One poller therefore generates at most about **1 status read/s**, or **1.25%** of the published **80 reads/s per organization** for fetching individual jobs, excluding retries and other clients. The three latest active definitions using cloud Extract specify a 1,800-second polling timeout. Three application attempts allow **3 × 1,800 = 5,400 seconds** of polling plus backoff, uploads and SDK overhead. This is a client budget, not observed latency. [Split loop](../../standard_step/split/llamacloud_split_adapter.py#L119) · [Extraction retry loop](../../standard_step/extraction/extract_pdf.py#L165) · [Provider rate limits](https://developers.llamaindex.ai/llamaparse/general/rate_limits/) |
